## 2. 目标与边界

老化管理的完整目标包含两条业务流程：

1. 老化开始：扫描流转单或单个 PRO，汇总待开始产品并批量提交。
2. 老化结束：扫描单个 PRO，查看老化信息，并判定 OK 或 NG。

当前后端只提供“老化开始”的扫码校验和提交接口，因此首期可交付范围仅为老化开始。老化结束、入库门槛和 NG 上报保留在完整设计中，但在接口补齐前不进入开发范围，也不使用本地假数据或复用不匹配的接口代替。

## 3. 原型理解

### 3.1 页面形态

- 设备目标：PDA，基准尺寸 480 × 800。
- 页面标题：老化作业。
- 完整形态使用“老化开始 / 老化结束”双模式切换。
- 主操作只支持扫码，不支持手动输入。
- 扫码区域的高度、样式和状态表现以 `JInputLayout` 扫码模式的组件规范为准；主按钮保持适合 PDA 操作的高度。
- 主要颜色：蓝色表示主操作，绿色表示可执行或成功，红色表示错误或 NG，橙色表示门槛未达标。

### 3.2 老化开始原型

页面由三部分组成：

1. 扫码区：支持流转单和单个 PRO。
2. 本次待开始列表：仅展示每台产品信息，不单独占用高度展示汇总卡片。
3. 提交区：按钮主文案显示“开始老化”，按钮内小字显示产品数、产品类型数和生产计划数；提交成功后清空本次列表并恢复扫码状态。

原型允许：

- 连续混扫流转单和单个 PRO。
- 一个流转单返回多台产品。
- 不同产品、不同生产计划加入同一次提交。
- 从待开始列表中删除单台产品或清空全部产品。

### 3.3 老化结束原型

老化结束仅支持单个 PRO。扫码后展示：

- PRO 编码和“老化中”状态。
- 产品型号、生产计划、开始时间、已老化时长。
- 当前计划老化比例、目标数量、当前 OK 数和入库门槛。
- OK 放行或 NG 上报不良。

原型脚本最终生效的 NG 规则为：来源固定为“老化不良”，选择不良现象后进入正常维修；维修完成后恢复到可重新老化状态，不进入复检。该规则与页面初始静态说明中的“NG 产品终态”存在历史文字冲突，后续实现应以脚本最终规则为准，并由后端接口再次确认。

## 4. 首期页面设计：老化开始

### 4.1 页面入口

`MainActivity` 中的“老化管理”菜单进入老化作业页面。首期直接进入老化开始，不展示一个无法操作的老化结束页面；待结束接口齐全后，再增加双模式切换。

### 4.2 页面结构

#### 顶部栏

- 标题：老化作业
- 副标题：产品老化开始
- 返回：返回主菜单

#### 扫码卡片

- 标题：扫码
- 使用 JiangCore 已封装的 `JInputLayout`，配置 `jInputMode="scan"`。
- 提示：扫描流转单 / PRO码。
- 说明：可连续混扫流转单和单个 PRO，不同产品、不同生产计划可以一起开始。
- 控件只接受扫码设备输入，页面不提供软键盘手动录入入口。
- 扫码触发、焦点、校验中、成功、失败、清空、防重复触发等交互均使用封装控件的既有能力和回调，页面层不再自建一套扫码交互。
- 页面层只接收控件输出的完整二维码文本，调用业务接口并把校验结果回传给控件显示。

#### 待开始列表

- `materialCode` 为待开始列表中的 PRO 码和唯一键。
- 同一个 PRO 码在待开始列表中最多出现一次。
- 合并接口结果时，同时检查返回列表内部重复和返回结果与页面已有列表重复。
- 重复产品不加入列表，不覆盖已有产品，也不影响同次返回中的其他有效产品。
- 返回对象缺少 `materialCode` 时视为无有效 PRO 码，不加入待开始列表。

每项展示：

- 产品标识：优先 `materialCode`，缺失时显示 `proMatId`。
- 产品名称：`partName`。
- 产品编号：`partCode`。
- 生产计划：`planOrderCode`。
- 来源：页面本地记录本次扫描使用的二维码文本；不写回接口 DTO。
- 删除按钮：仅从本次待提交列表移除，不调用后端。

#### 底部操作

- 主按钮使用两行文案：
  - 主文案：`开始老化`
  - 小字汇总：`共 N 台 · N 种产品 · N 个生产计划`
- 产品数量取当前去重后的列表条数。
- 产品类型按 `partCode` 去重；缺少 `partCode` 时不计入类型数。
- 生产计划按 `planId` 去重；缺少 `planId` 时可用 `planOrderCode` 兜底统计。
- 页面不再设置独立的汇总行或汇总卡片，避免占用 PDA 纵向空间。
- 列表为空时按钮禁用。
- 提交期间按钮显示加载状态并禁止重复点击。

### 4.3 页面状态

| 状态 | 页面表现 | 可执行操作 |
| --- | --- | --- |
| 初始/空列表 | 扫码控件处于待扫描状态，列表显示空状态，提交按钮禁用 | 扫码 |
| 扫码校验中 | 扫码控件显示校验状态，提交按钮暂时锁定 | 等待结果 |
| 扫码成功 | 合并返回产品，刷新列表和按钮小字汇总 | 继续扫码、删除、清空、提交 |
| 重复产品 | 按 PRO 码过滤重复项；全部重复时提示已存在，部分重复时只加入非重复产品 | 继续扫码 |
| 扫码失败 | 扫码控件显示错误状态和后端错误信息 | 重新扫码 |
| 提交中 | 列表保持可见，主按钮加载且不可重复点击 | 等待结果 |
| 提交成功 | 清空列表，按钮小字归零，扫码控件恢复待扫描状态 | 开始下一批扫码 |
| 提交失败 | 保留全部列表，展示后端错误信息 | 重试提交或调整列表 |

## 5. 接口设计映射

### 5.1 扫码校验

`POST /pro/proAgingPlan/beScanValid`

请求：

```json
{
  "qrCode": "扫描得到的原始二维码文本"
}
```

响应数据：`List<AgingProductDto>`。

处理规则：

1. 每次扫码都单独调用接口。
2. 返回值固定为列表：扫描 PRO 码时列表数量为 1；扫描流转单码时列表数量可能大于 1。
3. 新结果与页面已有列表合并，唯一键固定使用 PRO 码字段 `materialCode`。
4. 先对接口本次返回列表按 `materialCode` 去重，再过滤页面待开始列表中已经存在的 PRO 码。
5. 重复项不加入、不覆盖已有项；同次返回中的其他非重复产品正常加入。
6. 返回对象的 `materialCode` 为空时不加入列表，并按无有效 PRO 码处理。
7. 接口返回空列表时视为没有可开始老化的产品，不改变当前列表。
8. 产品是否已老化、正在老化、已入库或生产未完成，以后端校验结果为准，客户端不自行推导材料状态枚举。

当前接口没有提供“流转单总数、过滤数量和过滤原因”的结构化字段，因此首期不能精确实现原型中的“共 5 台，加入 2 台，过滤 3 台及原因明细”。若后端只返回有效产品，页面只能提示实际加入数量；若需要过滤明细，接口需补充结构化结果。

### 5.2 开始老化提交

`POST /pro/proAgingPlan/startAging`

请求：

```json
{
  "agingProList": [
    "beScanValid 返回的完整产品对象"
  ]
}
```

处理规则：

1. 提交当前页面按 `materialCode` 去重后的完整 `AgingProductDto` 列表，提交前再次校验不存在重复 PRO 码。
2. 不把产品对象转换成 ID 或二维码字符串。
3. 不给对象补造后端未返回的业务字段。
4. 只有后端成功响应后才清空页面列表。
5. 失败时完整保留列表，便于直接重试。

## 6. Android 结构建议

沿用当前 `zds` 模式，不新增框架层：

- `AgingActivity`：页面渲染、接收封装扫码控件的结果、列表操作和提交动作；不自行实现扫码输入交互。
- `AgingViewModel` 或现有 `ZdsViewModel` 中独立老化状态：保存待开始列表、加载状态和一次性反馈。
- `ZdsRepository`：封装两个老化接口，继续使用 `JiangApiCaller.safeApiCall` 和 `JiangResult`。
- `ZdsApi`：使用已经建立的两个接口声明。
- `AgingProductDto`、`AgingScanValidRequest`、`AgingStartRequest`：保持后端字段名不变。

待开始列表应保存在 ViewModel 状态中，以避免屏幕重建时丢失；扫码框文本和一次性 Toast 不需要持久化到本地存储。

## 7. 扫码控件与并发规则

- 页面使用 `JInputLayout` 的扫码模式，不直接使用普通 `EditText`。
- 不开放软键盘手动输入，不增加手动确认或手动提交扫码内容的按钮。
- 扫码触发、Enter 处理、焦点恢复、文本清理、状态展示和防抖逻辑全部遵循封装控件，不在 Activity 中重复监听或改写。
- 页面业务层只负责：接收扫码文本、调用 `beScanValid`、合并返回列表、处理本地产品去重。
- 提交期间禁止继续扫码、删除、清空和重复提交，避免页面列表与提交快照不一致；锁定与恢复方式使用扫码控件已有状态 API。
- Activity 离开前不自动提交，也不静默清空列表。

## 8. 错误反馈

- 后端业务错误优先显示接口 `message/msg` 原文。
- 网络异常显示页面内提示，不切换成覆盖整页的错误页，当前待提交列表必须保留。
- 重复产品属于页面本地提示，不作为接口错误。
- 所有错误除颜色外必须有明确文字；扫描失败后焦点回到输入框。

## 9. 老化结束的接口缺口

要实现完整原型，至少还需要以下后端能力：

1. 老化结束扫码校验：返回产品信息、老化开始时间、已老化时长和是否允许结束。
2. 老化 OK 提交：记录结束时间和 OK 结果，并返回放行/入库门槛结果。
3. 老化 NG 提交：提交产品、固定来源“老化不良”和不良现象。
4. 不良现象字典：确认是否复用现有字典接口及具体字典编码。
5. 当前生产计划老化门槛：返回比例、目标数量、当前 OK 数和达标状态。
6. 维修完成后的状态恢复：由后端保证产品可重新进入老化开始扫码校验。

以上接口未提供前，不实现结束页的 OK、NG、门槛进度或维修流转。

## 10. 验收场景

### 首期必须通过

1. 页面不弹出软键盘，不支持手动录入二维码。
2. 扫描单个 PRO，接口返回长度为 1 的列表并加入一台产品。
3. 扫描流转单，接口返回长度可能大于 1，并将返回产品全部加入列表。
4. 连续扫描不同生产计划，列表允许混合存在。
5. 同一次接口返回中存在重复 PRO 码时只保留一条。
6. 新扫描结果与页面已有产品重复时不再次加入；部分重复时仍加入其他非重复产品。
7. 删除单台、清空全部后按钮小字汇总同步更新。
8. 页面不存在独立汇总卡片；按钮显示“共 N 台 · N 种产品 · N 个生产计划”。
9. 扫码失败时保留原列表，扫码控件按自身错误恢复逻辑进入下一次扫描。
10. 空列表不能提交。
11. 提交使用完整产品对象列表，且 `agingProList` 中不存在重复 PRO 码。
12. 提交成功后清空并恢复扫码控件状态。
13. 提交失败后列表不丢失，允许重试。

### 后续接口补齐后验证

1. 只允许单个 PRO 执行老化结束。
2. 未开始老化、时长不足、已结束产品不能结束。
3. OK 正确更新放行数量和入库门槛。
4. NG 必选不良现象，来源固定为“老化不良”。
5. NG 产品进入维修，维修完成后可重新老化，不进入复检。

## 11. 风险与待确认项

- OpenAPI 将 `agingResult`、`repairResult` 仅标记为 `null`，实际类型和枚举值未定义。
- `beScanValid` 是否返回无效产品过滤明细尚不明确。
- `startAging` 成功响应是否包含新增老化记录或仅返回空对象尚不明确。
- 老化结束流程所需接口尚未提供。
- 原型静态文案与最终脚本对 NG 终态存在冲突，本文采用最终脚本的“进入维修、完成后重新老化”规则。
