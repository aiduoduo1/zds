# CCR-2100 / CCR-2100S 调光器监控系统技术方案

**版本：** V1.0（方案评审稿）  
**范围：** 工控机通过 GCAN-211 WiFi 转 CAN 网关，采集 CCR-2100 / CCR-2100S 调光器的运行状态、报警和绝缘电阻；数据接入现有 Java 后台。  
**本期边界：** 只读监控和诊断，不下发调光、开机、关机或主备切换命令。

---

## 1. 已确认的现场约束

1. 工控机、所有 WiFi 转 CAN 网关均接入同一个现场局域网。
2. 一个 WiFi 转 CAN 网关下，CAN 侧建议串接 3 至 5 台调光器。
3. 同一个网关下的调光器 CAN 波特率相同；调光器各自具有 CAN 地址（本方案按协议称为 `CCR_ID`）。
4. `CCR_ID` 只要求在同一个网关对应的 CAN 总线内唯一；不同网关下可重复。
5. 现场没有既有监控主机。因此本系统工控机是 CAN 通讯的唯一 `MASTER`。
6. GCAN-211 采用 WiFi 网络连接，CAN 模块直接接入现场电路板。

> 结论：系统不得把“15 台”或任意固定设备数量写死。设备的唯一键为 **网关标识 + CAN 通道 + CCR_ID**，其中网关标识由固定 IP 地址和项目内网关编号共同确定。

### 2.1 职责划分

| 组件 | 责任 | 不应承担的责任 |
|---|---|---|
| 工控机 CCR 采集服务 | 连接网关、轮询、协议解析、状态判定、本地缓存、断网补传、现场日志 | 直接作为业务展示页面、依赖外网才能采集 |
| Java 后台 | 设备台账、历史数据、报警中心、权限、报表、对外查询接口 | 直接跨网络连接现场 GCAN-211 |

### 2.2 推荐软件形态

采集端采用独立的 **Java 17 服务程序**，部署为 Windows 服务。它不是浏览器页面，也不依赖用户打开网页才工作。服务启动后持续运行；Web 页面和后台重启不应中断现场采集。

建议模块：

```text
ccr-gateway-agent
├─ gateway-connection       网关连接、收包、发包、重连
├─ gcan-codec               GCAN 网络数据流拆帧/组帧
├─ ccr-protocol             CCR 查询报文和响应解析
├─ polling-engine           每网关独立轮询调度
├─ state-and-alarm          状态机、数据新鲜度、报警生命周期
├─ local-store              SQLite 本地缓存、补传队列
├─ backend-adapter          对接现有 Java 后台（HTTP）
├─ configuration            网关、设备、策略配置
└─ diagnostics              日志、健康检查、原始报文诊断
```

## 3. 设备寻址、台账和动态管理

### 3.1 设备唯一键

```text
deviceKey = gatewayId + canChannel + ccrId
```

示例：

| gatewayId | 网关 IP | CAN 通道 | CCR_ID | deviceKey | 说明 |
|---|---|---|---|---|---|
| GW-A | 192.168.10.11 | CAN1 | 0x11 | GW-A/CAN1/0x11 | 网关 A 下第 1 组第 1 台 |
| GW-B | 192.168.10.12 | CAN1 | 0x11 | GW-B/CAN1/0x11 | 与上行不冲突 |

不得以 `CCR_ID` 单独作为数据库主键、前端列表键或报警唯一键。

### 3.2 配置方式

设备数量和归属必须动态维护，不写死 15 台。

网关配置至少包含：

- `gatewayId`：项目内唯一编号。
- `ip`、`port`：TCP Socket 地址。
- `canChannel`：GCAN 使用的 CAN 通道。
- `baudRate`：本通道 CAN 波特率。
- `masterId`：工控机在该 CAN 通道使用的 MASTER_ID。
- `enabled`：是否启用采集。
- `expectedDeviceCount`：仅用于运行校验，不是硬限制。

设备配置至少包含：

- `deviceKey`、`gatewayId`、`ccrId`。
- 设备名称、安装位置、所属回路/区域、主机或备机属性。
- 查询类型：主机 `0x61`、备机 `0x62`；绝缘查询 `0x11` 是否启用。
- 启用状态、离线阈值、备注。

### 3.3 自动发现

提供“扫描待确认设备”的调试功能，但不自动把发现设备纳入正式监控。

1. 在指定网关上按合法 `CCR_ID` 范围低频查询。
2. 收到合法 `0x63` 响应的设备记录为“待确认”。
3. 人员补充名称、位置、主/备属性后，才启用正式轮询。
4. 扫描只能由有权限的人员在调试窗口触发，并完整记录操作日志。

原因：自动扫描无法判断设备名称、实际位置和主备业务关系，不能直接替代设备台账。

## 4. 电气与网络设计边界

### 4.1 CAN 侧原则

1. 同一网关下的 3 至 5 台调光器采用 CAN_H / CAN_L 总线串接，避免星形接线和过长分支。
2. 总线仅在物理两端配置终端匹配电阻；通常为 120 Ω。GCAN-211 内置终端电阻是否启用，应以实际接线位置和拨码状态为准。
3. CAN_H、CAN_L 不可反接；屏蔽、接地和隔离按现场电气图及设备说明书实施。
4. 总线波特率必须与同一通道所有调光器一致。波特率不一致会造成持续超时或错误帧，不能靠软件补救。
5. 现场验收时必须测量总线两端断电电阻、检查终端位置和接线极性；程序只负责发现通讯异常，不替代电气验收。

### 4.2 WiFi/LAN 侧原则

1. 所有网关和工控机接入同一个受控局域网；多网关时必须使用共同的工业无线网络，而不是让工控机在多个设备热点之间切换。
2. 每台网关使用固定 IP 或 DHCP 地址保留，IP 不得变化、不得重复。
3. 工控机到网关的 TCP 端口必须可达；防火墙只放通必要网段和端口。
4. 现场网络不要求访问互联网；采集服务在后台服务器不可达时仍须运行。
5. 无线信号弱、丢包、漫游和短时断电按“网关通讯异常”处理，不直接判定为调光器故障。

## 5. 通讯与轮询设计

### 5.1 协议边界

- GCAN-211 与工控机：标准 TCP Socket。
- CCR：CAN 2.0B 扩展帧。
- 本方案按设备协议使用查询：主机 `0x61`、备机 `0x62`、绝缘电阻 `0x11`。
- CCR 状态响应：`0x63`，页地址 0 和页地址 1；两包正常间隔约 20 ms。
- 绝缘电阻响应：`0x13`。
- GCAN 普通数据流中，一条 CAN 帧为固定 13 字节；兼容模式为 20 字节。实际采用模式必须作为网关配置项，采集服务不可假定一次 TCP `read` 等于一条 CAN 帧。

### 5.2 报文处理规则

TCP 是字节流，可能出现半帧、粘包、多帧合并或断线截断。处理器必须：

1. 维护每条网关连接独立的接收缓冲区。
2. 仅在缓冲区达到完整帧长度后解析；不足时继续等待。
3. 一次读到多帧时全部依序解析。
4. 校验帧长度、扩展帧标志、DLC、CAN ID、命令类型和页地址。
5. 对非法帧计数并记录诊断日志；连续异常达到阈值后重建 TCP 连接。
6. 原始报文保存为十六进制诊断信息，不能用未校验的报文直接更新状态。

### 5.3 每网关独立轮询器

每个网关运行一个独立的串行轮询队列。同一网关一次只允许一个等待响应的查询，避免多个相同设备响应混淆；不同网关并发运行，互不阻塞。

建议默认参数（均可配置）：

| 参数 | 默认值 | 设计理由 |
|---|---:|---|
| TCP 连接超时 | 3 秒 | 避免不可达网关长时间占用线程 |
| 单次 CCR 查询等待 | 500 ms | 覆盖正常约 20 ms 的双包响应并保留无线余量 |
| 单次查询重试 | 1 次 | 降低瞬时无线丢包误判，避免总线过载 |
| 设备离线阈值 | 连续 3 个完整轮询周期失败 | 区分瞬时丢包与稳定离线 |
| CCR 状态采集周期 | 1 秒 | 3 至 5 台/网关的实时监控起点 |
| 绝缘电阻查询周期 | 60 秒 | 绝缘值变化通常不需要秒级轮询 |
| 网关恢复后的缓启动 | 0 至 3 秒随机抖动 | 防止多网关同时恢复时集中产生流量 |

一台设备的一次完整状态查询：

```text
发送 0x61 或 0x62（DLC=0）
→ 等待 0x63 页地址 0
→ 等待 0x63 页地址 1
→ 两页齐全：更新“有效状态”
→ 只有一页/超时：本轮失败或降级，不以半包覆盖完整旧状态
```

绝缘查询单独调度，避免把低频指标和实时状态耦合。返回 `0xFFFFFFFE` 时，按“绝缘值大于 1,000,000 KΩ”显示，不能误显示为负数或异常超大数。

## 6. 连接、重连与状态机

### 6.1 网关连接状态

```text
DISABLED → CONNECTING → ONLINE
                 │         │
                 │         ├─ Socket异常/连续无效帧 → RECONNECTING
                 │         └─ 管理员停用 → DISABLED
                 └─ 连接失败 → RECONNECTING

RECONNECTING → CONNECTING
RECONNECTING → OFFLINE（达到告警阈值，但仍继续后台重试）
```

- `ONLINE`：TCP 已建立且最近有有效协议通讯。
- `RECONNECTING`：正在退避等待或重建连接。
- `OFFLINE`：超过配置阈值无法恢复；状态是告警，不代表停止尝试。
- `DISABLED`：管理端明确停用，不重连、不报警。

### 6.2 重连策略

发生 TCP 断开、连接超时、连续收包异常或连续完整轮询失败时：

1. 立即关闭旧 Socket、取消该网关未完成请求、保留最后有效状态。
2. 使用退避延迟尝试重连：1 秒、2 秒、5 秒、10 秒、30 秒；后续固定 30 秒。
3. 每次延迟加入小范围随机抖动，避免网关集体断电恢复时同时冲击网络。
4. 重连成功后先读取和丢弃残留字节，随后按配置设备进行低速首轮查询。
5. 首轮完整成功后将网关恢复为 ONLINE；不能只因 TCP 建连成功就宣告设备正常。

### 6.3 设备状态

| 状态 | 含义 |
|---|---|
| DISABLED | 后台停用，不轮询 |
| UNKNOWN | 新配置或采集服务刚启动，尚未得到有效完整响应 |
| ONLINE | 最近完整响应有效 |
| DEGRADED | 有部分响应、数据过期或偶发失败，但未达到离线阈值 |
| OFFLINE | 网关在线但设备连续完整轮询失败达到阈值 |
| CHANNEL_OFFLINE | 所属网关离线，不能归因于单台设备 |

页面必须同时显示“状态值时间”和“通讯状态时间”。旧数据只能标为“最后一次有效值”，不得伪装成实时数据。

## 7. 数据解析与报警策略

### 7.1 采集数据

页地址 0 的 `0x63` 响应解析为：回路电流有效值、回路电压有效值、有功功率原始值、无功功率原始值。电流按照协议以 10 mA 为单位换算，电压以 V 为单位换算。功率单位或倍率如协议未明确，应先保留原始值和协议版本，不擅自换算。

页地址 1 的 `0x63` 响应解析为：工作光级、本地/遥控、接触器、上电、短路运行、主备切换、回路状态、坏灯数和报警字节。

`0x13` 响应解析为绝缘电阻值，单位 KΩ。

### 7.2 报警分类

| 分类 | 例子 | 发生条件 | 恢复条件 |
|---|---|---|---|
| 网关通讯 | Socket 建连失败、持续断开 | 网关重连失败达到阈值 | 建连且首轮有效通讯成功 |
| 设备通讯 | 单台 CCR 无完整响应 | 网关在线且该设备连续失败 3 周期 | 连续 2 个完整周期成功 |
| 数据质量 | 半包、无效 DLC、未知命令、数据过期 | 协议校验失败或超时 | 后续连续有效帧恢复 |
| 调光器故障 | 绝缘低、灯泡烧坏、通讯板故障、过流、外场开路、快熔坏等 | 对应协议位为 1 | 对应协议位连续有效帧恢复为 0 |
| 调光器告警 | 绝缘低预警、灯泡烧坏预警、温度预警等 | 对应协议位为 1 | 对应协议位恢复为 0 |
| 系统运行 | 本地缓存积压、磁盘空间不足、后台连续上传失败 | 达到配置阈值 | 阈值以下并完成恢复检查 |

协议中报警位至少包含：温度过高、绝缘阻值低、灯泡烧坏、监视板与 IRM 板通讯、监视板与主控板通讯、IGBT、电网频率、电网电压、输出电流与光级不符，以及回路过零中断、外场开路、快熔、过流、VA 跌落等。最终严重等级应由电气业务负责人确认后配置，不能仅凭软件自行决定安全等级。

### 7.3 报警生命周期与防风暴

每一条报警按 `(deviceKey, alarmCode)` 或 `(gatewayId, alarmCode)` 唯一定位：

```text
正常 → 发生 → 持续 → 已确认（人工动作，可选） → 恢复 → 归档
```

- “确认”不等于“恢复”；故障仍在时仍显示持续。
- 同一报警持续期间只更新最后出现时间和次数，不能每秒插入新事件。
- 瞬时通讯问题采用连续周期阈值；严重设备故障位可首帧上报，恢复时采用连续有效帧防抖。
- 网关离线时抑制其下所有“设备离线”重复报警，只保留网关级根因。
- 网关恢复后逐台确认，避免一次恢复产生大量重复恢复事件。

## 8. 本地存储、后台同步与断网补传

### 8.1 本地数据原则

工控机本地使用 SQLite，不依赖后台在线：

- 当前设备状态表：每台设备一条最新完整有效状态。
- 报警事件表：发生、持续、确认、恢复。
- 待上传队列表：带唯一事件 ID、创建时间、重试次数、状态。
- 原始报文诊断环形表：只保留最近 N 天或 N 条。
- 运行指标表：连接次数、重连次数、成功率、超时数、无效帧数。

状态采集值按策略入库，例如状态变化时立即存储、稳定状态按 1 分钟归档；不得把每次原始 CAN 帧无限制落盘。

### 8.2 上传与幂等

1. 采集到有效状态或报警变化，先写本地事务，再进入待上传队列。
2. 后台可用时批量上传；后台返回确认后，标记本地记录已送达。
3. 失败时按退避重试；网络恢复后按时间顺序补传。
4. 每条事件携带全局唯一 `eventId`，后台按 `eventId` 幂等入库，重复提交不得产生重复报警。
5. 后台连续不可达不影响现场采集和报警判定，只触发“后台同步异常”系统告警。

建议本地容量至少可保存 30 天报警和状态归档；最终保留期按设备数量、采样频率和工控机磁盘容量核算。

## 9. 界面、接口与权限

### 9.1 必备页面

1. **网关总览**：IP、在线状态、最后有效通讯、连接质量、下属设备数量、异常数量。
2. **调光器总览**：按网关/区域分组，显示设备名称、CCR_ID、在线状态、电流、电压、光级、主备、主要报警和最后更新时间。
3. **设备详情**：完整电参、绝缘值、状态位、全部报警、趋势、原始报文诊断摘要。
4. **报警中心**：当前报警、历史报警、确认记录、恢复时间、筛选导出。
5. **设备与网关配置**：维护网关、设备台账、启停、采集参数；修改需审计。
6. **运维诊断**：Socket 状态、轮询成功率、重连次数、缓存积压、日志下载、手动扫描。

### 9.2 后台接口边界

接口字段不在本方案阶段臆造，需与现有 Java 后台接口规范统一。至少应具备：

- 网关与设备配置下发/拉取。
- 当前状态批量上报。
- 报警发生、确认、恢复事件上报。
- 离线缓存批量补传确认。
- 采集服务健康心跳。
- 后台向工控机下发配置版本；工控机校验成功后回报生效版本。

采集端不能因后台配置下发失败而清空现有可用配置；始终保留“最后一次校验成功的配置”。

### 9.3 权限

本期只读，因此普通用户可查看，运维人员可查看诊断，管理员可改网关/设备配置。所有配置修改、手动扫描、启停设备均记录操作者、时间、旧值、新值和结果。

未来若加入控制功能，必须单独立项，至少具备角色权限、双重确认、操作原因、命令回执、失败回退、审计、联锁条件及紧急停止边界。本期不得通过调试界面任意下发 `0x60` 控制命令。

## 10. 日志、监控和可运维性

### 10.1 日志规范

采用滚动文件日志和结构化字段，至少保留：时间、级别、gatewayId、IP、deviceKey、CCR_ID、命令类型、耗时、结果码、异常摘要和关联请求 ID。

| 日志类别 | 内容 | 保留建议 |
|---|---|---:|
| 运行日志 | 服务启动、配置加载、状态切换、重连 | 90 天 |
| 通讯日志 | 连接、超时、发送/接收摘要、协议校验失败 | 30 天 |
| 原始报文诊断 | 十六进制收发帧，仅调试级 | 7 天或定量环形 |
| 审计日志 | 配置变更、扫描、启停、未来控制操作 | 长期保存 |
| 错误日志 | 未捕获异常、数据库/磁盘/上传异常 | 90 天 |

正常稳定轮询不得逐帧写 INFO 日志，以免磁盘被大量日志占满；可按采样率记录或仅写调试日志。

### 10.2 健康指标

采集服务每分钟统计并上报：

- 服务运行时长、版本、配置版本。
- 每个网关的连接状态、重连次数、最后有效通讯时间。
- 每台设备的查询成功率、超时数、最后有效数据时间。
- 无效帧数、协议解析失败数。
- 本地待上传队列长度、最旧未上传数据时间。
- SQLite 可用性、磁盘剩余空间、内存和 CPU 基础指标。

## 11. Windows 部署与故障恢复

1. 使用独立打包的 Java Runtime 部署，不要求现场人员安装 JDK、IDE 或 Android Studio。
2. 采集服务注册为 Windows 服务，设置开机自启、异常退出自动重启。
3. 配置、数据库、日志和程序目录分离；升级程序不得覆盖生产配置和本地缓存。
4. 升级前自动备份配置和 SQLite 数据库；升级后执行配置兼容性检查。
5. 工控机断电恢复后：服务自启 → 加载最后可用配置 → 逐网关重连 → 低速首轮轮询 → 恢复常规轮询与补传。
6. 服务提供本地健康检查接口，便于 Windows 任务或运维平台检测进程假死。

## 12. 现场调试与验收

### 12.1 上线前检查单

- [ ] 每台网关 IP、端口、WiFi 信号和工控机可达性确认。
- [ ] 每个 CAN 通道波特率确认，与调光器一致。
- [ ] CAN_H/CAN_L 接线、终端电阻、极性和屏蔽检查。
- [ ] 每台设备 `CCR_ID` 在所属网关/通道内唯一。
- [ ] 网关与设备台账、名称、位置、主备关系完成确认。
- [ ] 工控机磁盘、时间同步、Windows 自动启动和防休眠配置完成。
- [ ] 现场网络防火墙和后台访问权限完成验证。

### 12.2 必测异常场景

| 场景 | 预期结果 |
|---|---|
| 拔掉单台 CCR 通讯 | 仅该设备离线告警，其他同网关设备继续采集 |
| 关闭/断开一个网关 | 网关离线告警，下属设备显示 CHANNEL_OFFLINE，不产生报警风暴 |
| 恢复网关网络 | 自动退避重连，首轮成功后恢复，生成一次恢复事件 |
| 工控机到后台断网 | 采集不停、本地缓存增长，后台恢复后幂等补传 |
| 后台重启 | 工控机采集不停，恢复后继续上报 |
| TCP 粘包/半包 | 解析器正确缓存拼帧，不误更新状态 |
| 无效 CAN 帧 | 仅记诊断和数据质量计数，不污染有效状态 |
| 修改设备配置 | 新配置校验成功后生效；失败时保持旧配置 |
| 工控机重启 | 服务自动恢复，配置和未上传数据不丢失 |

## 13. 实施阶段与交接物

### 阶段 0：现场参数与方案确认

确认网关数量、IP/端口、CAN 通道、波特率、每网关设备清单、网络拓扑和后台接口规范。

### 阶段 1：只读通讯诊断

完成多网关连接、重连、GCAN 拆帧、CCR 查询/解析、原始报文诊断和离线状态机；不包含控制命令。

### 阶段 2：后台与监控页面接入

完成配置同步、SQLite 缓存补传、实时状态、报警中心、历史数据和运维页。

### 阶段 3：现场联调与验收

按本方案第 12 章逐项验证，形成网关/设备台账、网络图、接线确认记录和验收报告。

### 阶段 4：控制功能（后续独立立项）

只有在完成电气安全评审、权限设计和现场联锁验证后，才评估 `0x60` 调光/关机命令。

## 14. 方案确认项

以下内容作为实施前基线：

- 多网关、同一局域网、每网关下 3 至 5 台调光器。
- 设备地址以 `(gatewayId, canChannel, ccrId)` 唯一标识。
- 工控机是唯一 MASTER。
- 本期只读监控，控制命令禁止进入生产。
- 采集端独立运行、Windows 服务化、本地缓存、后台异步补传。
- 网关与设备均采用独立状态机、独立报警和独立重连。

确认本方案后，代码实现必须以本文件为边界；任何涉及接线、波特率、控制权限、报警等级或后台接口的变更，均应先更新本方案再实现。
