# 维修提交后快速复检设计

## 目标

正式提交维修结果时，根据维修结果字典的精确 `label` 决定是否允许复调；只有“已修好，允许复调”在提交成功后自动进入复检，其他最终状态必须在提交前二次确认。

## 提交分支

- 保存草稿 `DRAFT`：保持现有提交、提示与清空行为。
- 正式提交 `SUBMIT` 时，通过当前选中 value 在维修结果字典中查找对应 label。
- 仅当 label 精确等于“已修好，允许复调”时直接调用维修确认接口，不显示确认弹窗。
- 其他 label 在调用接口前显示不可从外部取消的确认弹窗：“该状态为最终状态，确认后无法继续使用，是否确认？”
- 最终状态弹窗确认后才调用维修确认接口；取消仅关闭弹窗，不发请求、不清空当前填写内容。
- 不根据字典 value 或 label 关键字进行判断。

## 成功后行为

- “已修好，允许复调”提交成功：保存维修页扫码框中的原始 SN/PRO 二维码，清空维修页，直接进入 `RecheckActivity`，不再显示“继续维修 / 去复检”弹窗。
- 其他最终状态提交成功：提示提交成功，清空维修页并留在维修功能，继续处理下一台。

## 复检接入

- 为 `RecheckActivity` 增加显式 `start(context, qrCode)` 入口。
- 入口参数必须使用维修扫码框原始内容，不使用接口返回的纯 `report.sn`。
- 复检页创建时将二维码写入现有扫码框，并在页面初始化完成后直接调用现有 `submitScanSn`，自动执行复检校验。
- 手动进入复检页、手动输入和普通扫码行为保持不变。

## 状态与异常

- 最终状态确认弹窗展示期间不发请求；确认提交后沿用现有按钮禁用和防重复提交状态。
- 字典尚未返回或 value 无法匹配 label 时按“其他最终状态”处理，不允许自动进入复检。
- 若传入二维码为空，复检页保持普通待扫描状态，不自动请求。
- 复检校验失败时继续沿用现有扫码错误提示和重新聚焦逻辑。
- 不修改维修提交接口、复检接口、ViewModel、Repository 或 DTO。

## 验证

- `DRAFT` 成功仍提示保存并清空。
- 精确 label“已修好，允许复调”不显示确认弹窗，提交成功后自动进入复检。
- 其他 label 提交前显示最终状态确认；取消不发请求，确认后只提交一次。
- 自动复检传递原始 SN/PRO 二维码，复检扫码框正确回显并自动发起校验。
- 复检页无启动参数时保持原行为。
